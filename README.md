# 饮库 DrinkDB

**203 款饮料的属性数据库 + 多维筛选界面 + 网友提交审核后台。**

糖分和甜度是两件事——「零度可乐」零糖但很甜，「伊利纯牛奶」有糖却几乎不甜。
碳酸也不只看有没有气，还要看**开盖放一天之后还剩多少**。这个库把这些都拆开记了下来。

## 二、界面逻辑

### 两排横滑（没筛选的时候）

**没选任何条件、没搜索、没排序**的时候，全部饮料分两排显示，**左右划着看**，不自动滚。

- 手机上两排通到屏幕两边，右边有一道渐隐，一眼看得出还能往右划；
- 划动是浏览器原生的横向滚动，惯性、边缘回弹都是系统手感，几乎不占 CPU；
- 停下来就完全静止；
- 切到筛选再切回来，滚动位置不会丢。

**为什么不做自动轮播**：做过一版，JS 逐帧平移。卡片一多（两排合计 400 多个 img）
就卡成幻灯片，手机上尤其明显。中途还踩了两个坑：CSS animation 会被系统的
「减少动态效果」直接关掉；暂停按钮如果顺带重新渲染，位置会清零跳回开头。
想清楚之后结论很简单——这种浏览场景本来就不需要动，交给浏览器原生滚动最省事也最顺。

### 筛选按钮是三态的

**点一下 = 要（蓝），点两下 = 不要（红），点三下 = 取消。**

比如「茶」点两下变红，意思是"我不要带茶的"。

- 同一行里：蓝色的之间是「或」，红色的之间也是「或」，两组再相减；
- 不同行之间：都得满足；
- 选中的条件会变成一排小标签显示在工具条下面，点标签上的 ✕ 就能去掉那一个。

一旦有任何筛选 / 搜索 / 排序，流动区立刻收起来，换成静态网格。
筛选状态会写进网址，可以直接分享，例如：

```
index.html#f=carb:0,sugar:0,c:3!&sort=sugar-asc&q=可乐
```

（`!` 结尾表示"不要"。上例 = 没气的 + 糖很少的 + 不要茶类。）

### 筛选行

哪一类 / 糖 / 甜度 / 气 / 冰镇 / 咖啡因 / 茶 / 奶 / 酒精 / 价格 / 好买吗 / 偷懒（快捷）

**几个别处没有的筛法：**

| 条件 | 意思 |
|---|---|
| 甜，但没糖 | 甜度 ≥3 星却几乎不含糖。代糖党的核心需求 |
| 有糖，却不甜 | 含糖 ≥6g 但甜度 ≤2.5 星。牛奶、酸奶这种乳糖型的 |
| 放一夜还有气 | 碳酸 >0 且放一夜剩余 ≥2 星 |
| 放一夜就没气 | 碳酸 >0 且放一夜剩余 ≤1 星 |
| 代糖不挂舌 | 没用代糖，或者用了但后味 ≤1.5 星 |

排序有 14 种，含糖分升降、甜度升降、气最冲的在前、**最经放的在前**、咖啡因、度数等。

## 三、产品图

**153 款有真实产品图**（长边 360px 的 JPEG，全部合计 3.1 MB）。其余 50 款是「泛指 / 自制 / 玩梗」
条目——比如「矿泉水（泛指）」「白开水（自家烧）」「煮饮料过滤法」——这些本来就没有对应商品，
用自动生成的矢量图，语义上更诚实。

图片优先级（`js/art.js`）：

1. 数据里写了 `img`（外部图片地址）→ 用外部图
2. `assets/img/manifest.js` 里登记了本地图 → 用本地图
3. 都没有 → 现场画一张矢量图

### 重新抓 / 补图

```powershell
node tools/fetch-images.js              # 抓还没图的（Bing 图片搜，优先挑电商 CDN 的商品图）
node tools/fetch-images.js --only coke-classic --redo --q "可口可乐 330ml 罐"
node tools/shrink-images.js             # 压到长边 360px（借无头浏览器 canvas，不用 npm 包）
node tools/image-report.js              # 看覆盖率、体积、哪些还没图
```

**手动补图**：把图片存成 `assets/img/<饮料id>.jpg`（id 见 `js/data/*.js`），
再跑一次 `node tools/shrink-images.js` 会自动登记进 manifest。

> 抓来的多是天猫 / 京东官方旗舰店的商品图。本库是非商业的个人整理，
> 但这不构成法律意见——要正式商用请自行确认图片授权。
> 想全部撤掉：删掉 `assets/img/*.jpg` 和 `manifest.js`，页面自动回退成矢量图，不会坏。

### 为什么压这么小

原图平均 158 KB。轮播那两排有 400 多个 `<img>`，而且它们是靠 `transform` 移动的，
`loading="lazy"` 照样会陆续加载——真机上等于要下 60 MB。压到长边 360px 之后
总体积 23.5 MB → 3.1 MB，手机上就没压力了。

## 四、你问的两个问题

### 1️⃣ 饮料数据库存在哪里？要放本地存储吗？

**分三层，各管各的：**

| 层 | 存在哪 | 内容 | 谁能改 |
|---|---|---|---|
| **① 底库** | `js/data/01~05-*.js`（纯文本文件，随代码走） | **203 款内置饮料**，是唯一真源 | 你改代码 |
| **② 已审核的网友提交** | 浏览器 `localStorage`（键名 `drinkdb.v1.approved`） | 审核通过后并入前台库 | 你在后台点「通过」 |
| **③ 待审队列** | 浏览器 `localStorage`（`drinkdb.v1.pending`） | 网友提交、还没审的 | 网友提交、你处理 |

**所以：底库不需要放 localStorage**，它是代码的一部分，文件夹复制到哪都在；
localStorage 只用来放「运行时新增的东西」（网友提交与审核结果）。

⚠️ **本地版的重要限制**：`localStorage` 是**按浏览器 + 按设备**隔离的。也就是说——

- 换一台电脑、换一个浏览器，你就**看不到**自己之前审的记录；
- 网友在他自己电脑上提交的东西，**不会传到你这里**。

这正是「本地版」和「上线版」的分水岭。要让网友的提交真正「传输到你的后台」，
**必须有一个服务器**。代码已经为此留好了接口：`js/store.js` 里的 `RemoteAdapter`，
把它替换掉 `LocalAdapter` 即可，前台代码一行都不用动。

**在本地版里怎么手动收提交？** 后台有「存个备份 / 读备份」：
你自己导出 JSON 存档，换电脑时再读回来，审核记录就跟着走了。

### 2️⃣ 导出 Excel

**所有访客都能用**，顶栏按钮：

| 按钮 | 导出内容 |
|---|---|
| **导全库** | **全部 203+ 款**，28 列全特征，`.xls` 直接双击用 Excel / WPS 打开 |
| 导出筛选结果 | 当前筛选/搜索/排序后的子集 |
| CSV | 同样的 28 列，UTF-8 BOM，通用性最好 |

导出的 28 列：类别、产品名、品牌、英文别名、含糖 g/100ml、糖分星级、甜度星级、代糖类型、
代糖后味、热量、是否碳酸、气泡强度、**放一天后气泡**、**开盖一天掉气**、冰镇、酒精、咖啡因、
含茶、含奶、含果葡糖浆、常规容量、包装、参考价、大众化、酸感、特征小结、备注、数据来源。

技术实现是「HTML 表格 + Excel MIME」，不需要任何第三方库，离线也能用。

## 五、上线方案

### 推荐组合：**Cloudflare Pages + Pages Functions + D1**（全免费）

| 部分 | 用什么 | 免费额度 |
|---|---|---|
| 前端托管 | Cloudflare Pages | 无限流量、无限请求 |
| 后端接口 | Pages Functions | 10 万次请求/天 |
| 数据库 | D1（SQLite） | 5 GB 存储、500 万行读/天 |
| 管理员登录 | Cloudflare Access（邮箱验证码） | 50 用户内免费 |

> 备选：**GitHub Pages**（只能放静态前端，没有后端）、**Vercel + Supabase**（也免费，Supabase 自带账号系统与行级权限，写起来更省事）。

### 我建议的网址名

| 类型 | 建议 | 费用 |
|---|---|---|
| **免费二级域名** | `yinku.pages.dev`　或　`drinkdb.pages.dev` | **¥0**，注册 Cloudflare 后自动分配，可自定义前缀 |
| 免费备选 | `drinkdb.netlify.app` / `yinku.vercel.app` / `你的名字.github.io/drinkdb` | ¥0 |
| 想要好记的独立域名 | `yinku.app` · `drinkdb.cn` · `yinku.fun` · `hejiu.ren` | 约 ¥30–90/年 |

**租用步骤（约 15 分钟）：**

1. 注册 <https://dash.cloudflare.com>（免费，邮箱即可）；
2. 左侧 **Workers & Pages → Create → Pages → Upload assets**，把 `F:\饮料统计\ds` 整个文件夹拖进去 → 得到一个 `xxxx.pages.dev` 网址；
3. 想叫 `yinku.pages.dev`：在 Pages 项目的 **Custom domains** 里把项目名改成 `yinku`（或新建项目时就叫 `yinku`）；
4. 想要独立域名：在 **Domain Registration** 买（如 `yinku.app`），或在国内阿里云/腾讯云买，然后把 DNS 指到 Cloudflare，在 Pages 里绑定；
5. 需要后端时，在项目里加 `functions/api/` 目录写接口，绑定 D1 数据库。

### 上线时必须改的三处

| # | 改什么 | 为什么 |
|---|---|---|
| 1 | **`admin.html` 的登录改成服务端鉴权** | 现在口令只存摘要、看不到明文，但校验仍在前端做，**懂技术的人可以直接改浏览器状态绕过**。要真隔离得靠 Cloudflare Access / Supabase Auth / 自签 JWT。 |
| 2 | **`js/store.js` 里把 `LocalAdapter` 换成 `RemoteAdapter`** | 否则网友的提交只存在他自己的浏览器里，你永远收不到。 |
| 3 | **`js/config.js` 的 `apiBase` 填上后端地址** | 前端据此切到远端接口。 |

接口契约已经按 RESTful 设计好了（`js/store.js` 顶部注释）：

```
GET    /api/beverages                  → { approved: [...] }        公开
POST   /api/submissions                → 任何人可提交
GET    /api/submissions?status=pending → 待审列表（需管理员 token）
POST   /api/submissions/:id/approve    → 通过（需管理员 token）
POST   /api/submissions/:id/reject     → 驳回（需管理员 token）
```

> 说句实话：在没有服务器的纯静态页面上，**「只有我能看后台、别人只能看前台」是做不到的**——前端代码对所有人都是公开的。
> 本地版的口令只挡「随手点进来的人」。真正的权限隔离一定要靠服务端。这是唯一需要花钱/花时间的地方，但都在免费额度内。

## 七、字段说明（`js/data/_schema.js` 里有完整版）

| 字段 | 含义 | 备注 |
|---|---|---|
| `sg` | 含糖 g/100ml | `0` = 标称无糖 |
| `s` | **糖分星级** 0–5（半星） | 「含多少糖」 |
| `sw` | **甜度星级** 0–5（半星） | 「喝起来多甜」——和糖分是两件事 |
| `sub` / `at` | 代糖类型 / 代糖后味 0–5 | 阿斯巴甜、三氯蔗糖、赤藓糖醇、甜菊糖苷… |
| `cb` | **气泡强度** 0–5 | `0` = 非碳酸 |
| `fd` | **放一天后剩余气泡** 0–5 | 开盖/摇过之后的真实体验，原创指标 |
| `flatLoss` | 自动派生 = `cb - fd` | 掉气幅度，越大越不经放 |
| `ice` | 冰镇更好喝 / 常温也行 / 冰了反而差 | |
| `abv` `cf` `tea` `dairy` `hfcs` | 酒精%、咖啡因 mg/100ml、含茶、含奶、含果葡糖浆 | |
| `ml` `pk` `p` | 容量 / 包装 / 参考价 | |
| `pop` `ph` | 大众化星级 / 酸感星级 | |

**图片**：默认用 `js/art.js` 现场生成矢量图（易拉罐 / 瓶 / 利乐砖 / 咖啡杯 / 奶茶杯 / 啤酒瓶，配色按类目 + id 哈希，稳定可复现）。数据里加 `img: 'https://...'` 就会优先用真实产品图。之所以没有内嵌真实照片，是因为网上抓的图有版权风险、外链也容易失效；需要的话随时可以补。

## 八、日常维护

```powershell
node tools/check-data.js    # 改完数据跑一下：字段完整性 + 逻辑校验
```

新增饮料：在 `js/data/` 里对应的分册末尾加一行 `B({...})`，`id` 不能重复，然后跑上面的校验。
改完前台逻辑或样式，打开 `selftest.html` 跑一遍 40 项检查。

数据免责：糖分、热量、价格为常见规格的参考值，不同批次、口味、地区可能不同，请以实际包装标签为准。本库是信息整理工具，不构成健康或营养建议。
